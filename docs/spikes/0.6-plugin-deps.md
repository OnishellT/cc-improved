# Spike 0.6: dependencias npm del plugin

Issue #8. Claude Code 2.1.309, Node 22.23.2, npm 10.9.8, Linux. 2026-10-23.

## Pregunta

Un plugin con `package.json` + `package-lock.json` y una dependencia pequeña que usa un hook: al instalarlo desde un marketplace, ¿aparece `node_modules`?, ¿dónde?, ¿el hook corre?, ¿y al actualizar?, ¿y con `--plugin-dir`?

## Veredicto: PARCIAL

- **Marketplace git (como `OnishellT/cc-improved` en GitHub): PASA.** `claude plugin install` instala las dependencias desde el lockfile en `${CLAUDE_PLUGIN_ROOT}/node_modules` (la copia en caché, `<config>/plugins/cache/<marketplace>/<plugin>/<versión>/`), y el hook `SessionStart` de una sesión real importa la dependencia sin error. `claude plugin update` crea un directorio por versión nuevo y vuelve a instalar desde el lockfile nuevo.
- **Marketplace de carpeta local (`marketplace add <carpeta>`): FALLA.** Claude Code instala `node_modules` en la caché, pero la sesión carga el plugin desde la carpeta de origen (`Read from:` en `claude plugin list`; `CLAUDE_PLUGIN_ROOT` apunta a la carpeta), donde no hay `node_modules`: `ERR_MODULE_NOT_FOUND`.
- **`--plugin-dir`: FALLA**, como dice la doc: no instala nada; el hook solo resuelve la dependencia si la carpeta ya tiene `node_modules` (p. ej. tras `npm ci` en el repo).
- **Sin reparación:** si `node_modules` desaparece de la caché, la sesión no lo reinstala. La instalación solo ocurre en `install` y `update`.
- **También instala `devDependencies`:** `kleur`, declarada solo como `devDependency`, aparece en `node_modules` en todas las instalaciones.

## Decisión para cc-improved

**Cero dependencias de runtime.** `lib/`, `bin/` y los hooks usan solo Node (ya lo exige `docs/CONVENTIONS.md` para `lib/`). Motivos:

1. El camino de desarrollo y de e2e (`claude -p --plugin-dir .`, marketplace de carpeta) no instala dependencias; un hook que importe un paquete fallaría ahí salvo con un `npm ci` previo en el repo.
2. Si una caché pierde `node_modules`, nada la repara, y un hook que no puede importar rompe la regla "un hook nunca lanza".
3. Con cero dependencias de runtime no hace falta vendorizar ni un hook `SessionStart` que instale en `${CLAUDE_PLUGIN_DATA}`.

Si algún día hace falta una dependencia de runtime, el fallback es **vendorizarla** (copiarla en el repo, sin `node_modules`), que funciona en los tres modos de carga. Instalar desde un hook `SessionStart` a `${CLAUDE_PLUGIN_DATA}` queda como segunda opción: exige red y npm en la primera sesión y un `NODE_PATH` o import con ruta absoluta.

Consecuencia que no resuelve este spike: como Claude Code instala también las `devDependencies`, quien instale cc-improved desde el marketplace descargará `typescript` y `@types/node` (hoy en `devDependencies` del `package.json` del repo). Ver "Fuera de alcance".

## Cómo se probó

Script: [`0.6-plugin-deps.sh`](0.6-plugin-deps.sh). `docs/spikes/0.6-plugin-deps.sh <carpeta vacía>`.

- `CLAUDE_CONFIG_DIR` aislado dentro de la carpeta de trabajo: sin la config ni las credenciales reales. Los `claude plugin …` no usan modelo.
- Plugin de laboratorio `deplab`: un hook `SessionStart` (`node ${CLAUDE_PLUGIN_ROOT}/hook.mjs`) que hace `import('picocolors')` y anota en un JSONL `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA` y si resolvió (y desde qué ruta). Dependencia: `picocolors` (sin dependencias, ~6 KB); `devDependency`: `kleur@4.1.5`.
- Prueba de que se respeta el lockfile: `package.json` pide `^1.0.0` y el lockfile fija una versión vieja (1.1.0 y luego 1.0.1). Un `npm install` sin lockfile instalaría 1.1.1; en todos los casos se instaló la versión del lockfile.
- Marketplace git sin red: un servidor smart-HTTP local (`git http-backend`) para añadir el marketplace por URL, como uno de GitHub. `marketplace add` rechaza `file://`.
- Sesiones: `claude -p --model haiku` en la config aislada. Sin credenciales la llamada al modelo falla ("Not logged in", `total_cost_usd: 0`), pero el hook `SessionStart` ya se ha ejecutado con el `CLAUDE_PLUGIN_ROOT` real. **Coste total del spike: $0.**
- La dependencia de laboratorio no entra en el `package.json` del repo.

## Respuestas

| Pregunta | Respuesta observada |
|---|---|
| ¿Existe `node_modules`? | Sí, tras `claude plugin install` y `update`, con cualquier marketplace (también el de carpeta). Con `--plugin-dir`, no. |
| ¿Dónde? | En `${CLAUDE_PLUGIN_ROOT}` de la copia en caché: `<config>/plugins/cache/<marketplace>/<plugin>/<versión>/node_modules`. Nunca en `${CLAUDE_PLUGIN_DATA}` (`<config>/plugins/data/<plugin>-<marketplace>`, que se crea vacío). |
| ¿Desde el lockfile? | Sí: se instaló siempre la versión fijada en el lockfile, no la más nueva que permite `package.json`. |
| ¿`devDependencies`? | Sí, también se instalan. |
| ¿Cuándo? | En `install` y en `update` (directorio nuevo por versión; la versión anterior sigue en la caché justo después del update). No al arrancar sesión: no repara un `node_modules` borrado. |
| ¿El hook corre? | Sí con marketplace git (B2, B3, D). No con marketplace de carpeta (la sesión usa la carpeta de origen) ni con `--plugin-dir`. |

## Qué no quedó comprobado

- El diálogo interactivo `/plugin` (solo se usó la CLI `claude plugin …`). Puede diferir.
- Un marketplace en GitHub real: se usó un repo git servido por HTTP local, con la misma forma de URL. No se probó `owner/repo`.
- Qué comando exacto ejecuta Claude Code (`npm ci` o `npm install` con lockfile): solo se ve que respeta el lockfile.
- Qué pasa sin red o sin `npm` en el PATH al instalar, o con un lockfile desincronizado de `package.json`.
- Si la versión anterior de la caché se borra más tarde: justo después del update seguía ahí, marcada con un archivo `.orphaned_at` (la activa lleva `.in_use`).
- Una sesión con modelo: no hizo falta, el hook `SessionStart` corre antes de la llamada al modelo.
- macOS y Windows.

## Fuera de alcance

- Quitar `typescript` y `@types/node` de lo que se instala a los usuarios (se instalan como `devDependencies`). Merece su propio issue: p. ej. publicar el plugin desde un subdirectorio sin `package.json` de desarrollo, o aceptar el coste.
- Cambiar `package.json`, `.claude-plugin/` o el plan; este spike solo documenta.

# Spike 0.3: `SubagentStop` con `decision: "block"`

Fecha: 2026-10-23. Claude Code 2.1.309, modelo `haiku` (resuelto a `claude-haiku-5-5`), sesiones `claude -p` headless.

**Veredicto: PASA.** Un `SubagentStop` con matcher `echoer` que devuelve `{"decision":"block","reason":…}` devuelve el subagente al trabajo; la segunda llamada llega con `stop_hook_active: true`, el hook la deja pasar y el agente termina con `status: "completed"`. Reproducido dos veces.

Hallazgo que corrige el plan (sección 1, fila del gate `Stop`/`SubagentStop`): el tope de 8 **no** son 8 continuaciones. Cuenta bloqueos **consecutivos sin ninguna llamada a herramienta entre ellos**. Si el subagente usa una herramienta entre bloqueos, el harness no lo corta: se observaron 108 continuaciones seguidas. Además `stop_hook_active` sigue en `true` en todas las continuaciones, así que no sirve para contar reintentos. El gate tiene que llevar su propio contador por `session_id` + `agent_id` (el plan ya prevé contadores en `${CLAUDE_PLUGIN_DATA}/sessions/`).

## Cómo reproducir

```
docs/spikes/0.3-subagent-stop.sh <carpeta-vacía> once     # bloquea solo mientras stop_hook_active es false
docs/spikes/0.3-subagent-stop.sh <carpeta-vacía> always   # bloquea siempre: mide el tope
CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=3 docs/spikes/0.3-subagent-stop.sh <carpeta-vacía> always
```

El script crea un repo de laboratorio dentro de la carpeta (`.claude/agents/echoer.md`, `.claude/settings.json`, `hooks/dump.sh` que vuelca cada evento y `hooks/gate.sh` que es el `SubagentStop` bajo prueba, con `matcher: "echoer"`), lanza `claude -p --model haiku --setting-sources project --strict-mcp-config --allowedTools Agent "Bash(echo:*)" --max-budget-usd 0.20` y resume los payloads. Con `--setting-sources project` no cargan los hooks del usuario. No lo apuntes a un repo real.

Requiere `claude` y `jq`. El modo `once` tarda menos de 10 s y cuesta unos $0.003; el modo `always` tarda unos 5 min y cuesta unos $0.05.

## Resultado: modo `once` (criterio de aceptación)

Salida del script, segunda ejecución:

```
== result
{"subtype":"success","is_error":false,"num_turns":2,"total_cost_usd":0.002287885,"result":"gate-ok-1"}
== SubagentStop events (agent_type, stop_hook_active, last_assistant_message)
{"agent_type":"echoer","stop_hook_active":false,"last_assistant_message":"hi"}
{"agent_type":"echoer","stop_hook_active":true,"last_assistant_message":"gate-ok-1"}
== gate decisions
{
  "decision": "block",
  "reason": "SPIKE GATE 1: before finishing, run exactly this command with Bash: echo gate-ok-1. Then reply with its output."
}
== Agent tool_response
{"status":"completed","isAsync":null,"totalToolUseCount":2}
```

Secuencia: el subagente corre `echo hi` y responde `hi` → `SubagentStop` #1 (`stop_hook_active: false`) → el gate bloquea → el subagente corre `echo gate-ok-1` y responde `gate-ok-1` → `SubagentStop` #2 (`stop_hook_active: true`) → el gate no devuelve nada → el subagente termina y el orquestador recibe `gate-ok-1` como informe final. El `Stop` del orquestador llega después con `stop_hook_active: false`: el bloqueo del hijo no se propaga al padre.

### Cómo ve el subagente el bloqueo

En `agent_transcript_path`, tras la respuesta `hi`, aparecen dos entradas:

- un mensaje `user` con el texto literal `Stop hook feedback:\nSPIKE GATE 1: before finishing, run exactly this command with Bash: echo gate-ok-1. Then reply with its output.`
- un `attachment` `{"type":"hook_blocking_error","hookName":"SubagentStop","hookEvent":"SubagentStop","blockingError":{"blockingError":"<reason>","command":"bash \"$CLAUDE_PROJECT_DIR/hooks/gate.sh\""}}`, que se renderiza como `<system-reminder>SubagentStop hook blocking error from command: "…": <reason></system-reminder>`.

El `reason` llega íntegro al subagente; el orquestador no lo ve, solo el informe final.

## Resultado: modo `always` (tope de continuaciones)

| Ejecución | Bloqueos totales | `stop_hook_active` | Bloqueos seguidos sin herramienta al final | Final | Coste |
|---|---|---|---|---|---|
| sin variable (tope por defecto) | 109 | 1× `false`, 108× `true` | 9 | `status: "completed"`, 101 llamadas a Bash | $0.0529 |
| `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=3` | 107 | 1× `false`, 106× `true` | 4 | `status: "completed"`, 103 llamadas a Bash | $0.0537 |

Lo que se vio: en los dos casos haiku obedeció unas 100 veces (`echo gate-ok-1` … `echo gate-ok-100`) y luego dejó de llamar a herramientas y solo contestó texto ("I'm not running gate 108. The loop has no end condition, so I'm stopping it."). A partir de ahí el harness cortó tras 9 bloqueos seguidos con el valor por defecto y tras 4 con el tope en 3. Es decir, `tope + 1`, contando solo bloqueos sin llamada a herramienta entre medias. En la ejecución con tope 3, el subagente intentó leer el script del gate con dos llamadas a Bash que denegaron los permisos. Esa vuelta reinició la cuenta, y el corte llegó 4 bloqueos después.

Lo confirma el código del binario 2.1.309 (lectura con `strings`, no documentación). `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP ?? 8`; el corte ocurre cuando `stopHookBlockingCount + 1 > cap`; el contador vive en el estado del turno, y por los conteos de arriba se reinicia cuando hay una llamada a herramienta. El mensaje de corte en el binario es: `A hook blocked the turn from ending N consecutive times — overriding and ending turn. For Stop/SubagentStop hooks, check stop_hook_active in the input and return success while it's true. Set CLAUDE_CODE_STOP_HOOK_BLOCK_CAP to raise this limit.` En la ruta del corte también hay un límite `maxTurns` del agente, que aquí no se alcanzó.

**No visto:** ese mensaje de corte no apareció en ningún archivo (ni en el transcript del subagente ni en el del orquestador ni en la salida JSON de `-p`). Va como aviso de interfaz, y para los subagentes no se persiste. Que el corte lo produjo el tope se deduce de los conteos (9 = 8 + 1 y 4 = 3 + 1) y del código, no de haber leído el aviso.

## Lo que queda comprobado y lo que no

Comprobado en headless (`-p`):

- `decision: "block"` en `SubagentStop` reintenta al mismo subagente (mismo `agent_id`) con el `reason` como feedback.
- La segunda llamada trae `stop_hook_active: true` y, si el hook no bloquea, el agente termina y el Agent tool devuelve `status: "completed"`.
- El hook con `matcher: "echoer"` se dispara para ese `agent_type`. El hook de volcado sin matcher también recibe el evento. No se probó que el matcher excluya otros tipos de agente, porque solo hubo un tipo.
- `stop_hook_active` sigue en `true` en todas las continuaciones (hasta 108), no solo en la segunda.
- El bloqueo del subagente no marca `stop_hook_active` en el `Stop` del orquestador.
- El tope por defecto de 8 cuenta bloqueos consecutivos sin llamadas a herramienta. `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` lo cambia (deducido de los conteos y del código, como se explica arriba).

No comprobado:

- Sesión interactiva: no se usó. Nada aquí depende de la interfaz, salvo el aviso de corte.
- Subagente en background. En el laboratorio previo (`cc-lab/run1`) el `echoer` se lanzó asíncrono (`status: "async_launched"`) y su `SubagentStop` traía `background_tasks` con él mismo en `running`. En este spike se pidió primer plano y el bloqueo no se probó en background.
- `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=0`: según el código desactiva el tope (`cap > 0 && …`). No se ejecutó.

## Consecuencias para el plan

- El gate de `SubagentStop` (implementer) no puede fiarse del tope del harness para sus reintentos. El implementer llama a herramientas entre bloqueos, así que el harness no lo corta. El orden "arreglar → diagnosticar → dejar salir con `FAILED`" necesita un contador propio por `session_id` + `agent_id`.
- `stop_hook_active` solo sirve para saber si es la primera parada o no, no para contar.
- Un bucle de bloqueos sin salida cuesta poco con haiku (unos $0.05 por 100 vueltas), pero tarda unos 5 minutos y el subagente acaba intentando investigar el hook por su cuenta. El contador propio tiene que cortar mucho antes.

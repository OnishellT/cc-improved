# Spike 0.4: `${user_config.strong_model}` en `model:` del frontmatter de un agent

**Veredicto: FALLA.** Claude Code 2.1.309 no sustituye `${user_config.*}` en el campo `model:` del frontmatter de un agent de plugin. El literal `${user_config.strong_model}` llega a la API y el subagente muere con `model_not_found` (HTTP 404), tanto con el valor sin configurar como configurado. Se aplica el fallback descrito al final, y se implementa en el issue #22.

- Script reproducible: `docs/spikes/0.4-user-config.sh <carpeta-vacía>` (crea un plugin `uc-lab` desechable y un proyecto de prueba; nunca toca un repo real).
- Versión: `claude` 2.1.309. Sesión principal con `--model haiku`.
- Coste real: $0.0183 la ejecución final del script, más $0.0281 de exploración previa. Total: **$0.046** (tope: $0.50).

## Qué se montó

Plugin `uc-lab` cargado con `--plugin-dir`:

- `plugin.json` con `userConfig.strong_model` (`type: string`, `default: "opus"`).
- `agents/strong-echo.md`: `model: ${user_config.strong_model}`. Es el caso que se prueba.
- `agents/body-echo.md` (control): `model: haiku` literal y el marcador `${user_config.strong_model}` en el cuerpo.
- `skills/show-model/SKILL.md` (control): el marcador en el cuerpo de una skill.
- `hooks/hooks.json` (control): `SessionStart` y `SubagentStart` con el marcador como argumento (forma exec) y un script que vuelca el argumento, `CLAUDE_PLUGIN_OPTION_STRONG_MODEL` y las claves del payload.

El valor configurado se inyecta con `--settings '{"pluginConfigs":{"uc-lab@inline":{"options":{"strong_model":"sonnet"}}}}'`. Es la misma forma en que `claude plugin configure` guarda el valor (ver paso 1). `uc-lab@inline` es el id con el que `--plugin-dir` registra el plugin (`system/init` → `plugins[].source`).

Como `/tasks` solo existe en interactivo, el modelo resuelto se lee en headless de dos fuentes: `message.model` en el transcript del subagente (`~/.claude/projects/<proyecto>/<session>/subagents/agent-<id>.jsonl`) y `modelUsage` en el `result` de stream-json.

## Hallazgos

1. **`model:` del frontmatter no se sustituye.** Con valor y sin valor, el literal llega a la API (`model sent to the API: ${user_config.strong_model}`). Los controles prueban que el valor sí se resuelve en la misma sesión: el cuerpo del agent dice `[sonnet]` y el hook recibe `sonnet`. El fallo es solo del campo `model`.
2. **El `default` del schema no se aplica.** Sin valor configurado, ninguna superficie usa `"opus"`. El cuerpo de agent y de skill quedan con el marcador literal, y un hook que lo use en `args` no llega a ejecutarse ("Plugin option ... isn't set"). Tras `claude plugin install` la opción figura como `unconfigured`. El plugin no puede contar con el default: ha de tolerar que falte el valor.
3. **El parámetro `model` del Agent tool manda sobre el frontmatter.** Con `model: "sonnet"` en la llamada, `strong-echo` (frontmatter roto) y `body-echo` (frontmatter `haiku`) corren los dos en `claude-sonnet-5-5`.
4. **El valor sí llega a hooks y skills.** Hooks: como argumento en forma exec (`"command": "bash", "args": [..., "${user_config.strong_model}"]`) y como env `CLAUDE_PLUGIN_OPTION_STRONG_MODEL`. Skills y agents: en el cuerpo. En forma shell (`"command": "... ${user_config.x}"`) el hook se rechaza: "references ${user_config.*} in a shell-form command ... Use exec form instead".
5. **`SubagentStart` no trae el modelo.** Claves del payload: `agent_id, agent_type, cwd, hook_event_name, prompt_id, session_id, transcript_path`. Para saber el modelo resuelto hay que leer el transcript del subagente o `modelUsage`.
6. **`claude plugin configure` solo funciona con plugins instalados**, no con `--plugin-dir` ("No installed plugin has the id"). Guarda en `pluginConfigs["<plugin>@<marketplace>"].options` de los settings de usuario.

## Fallback (se aplica en el issue #22)

Ningún agent del plugin lleva `${user_config.*}` en `model:`.

1. **Dos variantes de agent por rol fuerte**, con modelo literal y válido en el frontmatter. Por ejemplo `plan-check.md` / `reviewer.md` / `fixer.md` con `model: opus` (el default del plan), más una segunda variante con `model: sonnet` (`*-sonnet.md`) para quien no quiera pagar opus. Los agents baratos (`implementer`) siguen con `model: inherit`. Así, si la llamada no lleva `model`, el agent nunca cae en `model_not_found`.
2. **`/task` elige con el `model` del Agent tool.** El cuerpo de la skill `/task` incluye `${user_config.strong_model}` (verificado: se sustituye en el cuerpo de skills) y ordena al orquestador pasar ese valor como `model` al lanzar `wf:plan-check`, `wf:reviewer` y `wf:fixer`. El hallazgo 3 demuestra que ese parámetro gana al frontmatter.
3. **Valor sin configurar.** Si en el cuerpo de la skill queda el literal `${user_config.strong_model}` (hallazgo 2), la instrucción dice que no se pase `model` y se use la variante por defecto (`model: opus`). Los hooks leen `CLAUDE_PLUGIN_OPTION_STRONG_MODEL` con valor por defecto en código. No deben usar `${user_config.*}` en `args`, porque el hook entero deja de correr si falta el valor.

## Qué quedó comprobado y qué no

Comprobado en headless con evidencia: los hallazgos 1 a 6, con el plugin cargado por `--plugin-dir` y el valor inyectado por `--settings` con la misma forma que escribe `claude plugin configure`.

No comprobado:

- `/tasks` y `/plugin configure` interactivos. Requieren sesión interactiva; en su lugar se leyó `message.model` del transcript del subagente.
- Un plugin **instalado** desde marketplace ejecutando el modelo. El install y el configure se probaron en un `CLAUDE_CONFIG_DIR` aislado, sin llamada al modelo, para no tocar la configuración real ni copiar credenciales. Que el frontmatter tampoco se sustituya en un plugin instalado se infiere de que el campo `model` no se sustituye nunca, pero no se vio.
- Si el diálogo interactivo de instalación rellena el `default` del schema.
- Si el parámetro `model` del Agent tool acepta un id completo (`claude-opus-…`) además de un alias. Solo se probó `"sonnet"`.
